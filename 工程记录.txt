## 1. 抗噪实验任务背景与项目现状（2026-10-13）

### 1.1 总目标

后续将在实验室服务器上完成三个捆绑推荐模型在三个数据集上的抗噪实验。实验要检验：当训练期用户—捆绑（User-Bundle，UB）交互被人为注入不同程度的随机错误边后，各模型的推荐性能如何变化，以及 ReCoBR 相对两个已有论文模型是否具有更好的抗噪性。

本地机器不用于训练；本地只承担代码阅读、实现、配置整理和脚本准备。最终期望的交付形态是：项目同步至服务器后，只需执行一条总控命令，脚本即可自动生成噪声数据、依次运行全部实验、保存配置与日志，并汇总结果。

### 1.2 三个模型的归属与代码位置

1. **CrossCBR**：其他论文的公开基线模型，目录为 `CrossCBR/`。
   - 采用 UI（用户—物品）与 UB（用户—捆绑）两个视图。
   - 在两个视图上进行图传播，以 BPR 为主损失，并使用跨视图对比学习。
   - 入口：`CrossCBR/train.py`；模型：`CrossCBR/models/CrossCBR.py`。

2. **MultiCBR**：其他论文的公开基线模型，目录为 `MultiCBR/`。
   - 采用 UB、UI、BI（捆绑—物品）三个视图。
   - 对三张二部图分别传播、聚合，再使用配置中的模态与层权重融合。
   - 入口：`MultiCBR/train.py`；模型：`MultiCBR/models/MultiCBR.py`。

3. **ReCoBR**：本项目自己的方法，位于仓库根目录。
   - 源码内部的 CBR 分支类名为 `AnchorViewBundleNet`，DWT 分支类名为 `DWT`；后续报告、脚本、日志目录和实验表格统一使用名称 **ReCoBR**。
   - 模块一：利用外部预训练 UB 表示，对用户已观测 bundle 集合进行潜在扩散净化，并只在该用户原始已观测 UB 边中筛选 Top-K 高置信边，得到训练期净化 UB 图。
   - 模块二：以 UB 为锚点，在多视图融合前对齐 UB—UI 和 UB—BI 的用户侧与 bundle 侧表示。
   - 当前默认配置：NetEase、Youshu 使用 CBR 分支；iFashion 使用 DWT 分支。DWT 在最终打分时融合 UI、BI 表示，UB 视图主要服务训练期结构与对比约束。
   - 入口：`train.py`；模型：`models/model.py`；配置：`config.yaml`。

### 1.3 数据集与数据格式

三个数据集均使用整数 ID，规模如下：

| 数据集 | 用户数 | Bundle 数 | Item 数 | 原始训练 UB 边数 |
| --- | ---: | ---: | ---: | ---: |
| Youshu | 8,039 | 4,771 | 32,770 | 34,416 |
| NetEase | 18,528 | 22,864 | 123,628 | 217,864 |
| iFashion | 53,897 | 27,694 | 42,563 | 1,213,676 |

每个数据集包含：

- `user_bundle_train.txt`：本次抗噪实验唯一允许改写逻辑的数据源，即训练 UB 边；
- `user_bundle_tune.txt`、`user_bundle_test.txt`：验证与测试标签，原则上保持原样；
- `user_item.txt`：UI 图，保持原样；
- `bundle_item.txt`：BI 图，保持原样；
- `*_data_size.txt`：用户、bundle、item 总数，保持原样；
- iFashion 另有原始字符串 ID 映射 JSON 文件，保持原样。

根目录 `datasets/` 与 `MultiCBR/datasets/` 的同名数据内容已经核对一致。CrossCBR 自带 `CrossCBR/dataset.tgz`，服务器运行前需要在 `CrossCBR/` 下解压为其自己的 `datasets/` 目录。

### 1.4 抗噪定义（当前任务的字面实现目标）

对每个模型、每个数据集、每个噪声比例 x，构造一份新的训练 UB 文件。噪声比例集合固定为：

`0, 0.05, 0.10, 0.15, 0.20, 0.25`

对任意用户 u，设其原始训练交互集合为 T_u，交互数为 n_u：

1. 按比例 x 从 T_u 中随机、不放回地选择 m_u 条已有训练交互作为被替换边；
2. 从该用户在训练集中**未交互过**的 bundle 中随机、不放回地抽取 m_u 个 bundle；
3. 用新抽到的 m_u 条 UB 边替换被移除的 m_u 条边。

例如，x=0.50 且某用户有 20 条训练 UB 交互时，随机移除其中 10 条，并随机补入 10 条该用户原训练集中没有交互过的 bundle。替换后每位用户的训练 UB 度数保持不变，整份训练图的总边数也保持不变；变化只来自正确边被随机错误边替代。

噪声比例为 0 时必须严格等于原始训练数据，作为无噪声基线。

### 1.5 实验矩阵与公平性原则

实验总量为：3 个模型 × 3 个数据集 × 6 个噪声比例 = **54 组正式训练实验**。

对于同一个“数据集 × 噪声比例”，三个模型必须使用同一份生成后的 UB 训练边，或至少使用同一个固定随机种子和完全相同的生成算法，以确保模型间差异来自模型本身，而不是不同的噪声采样结果。

每一组实验应至少保存：

- 模型名、数据集、噪声比例、数据噪声随机种子、训练随机种子；
- 原始/替换后的边数、受影响用户数、每用户替换数统计；
- 实际运行配置快照；
- 完整标准输出日志、TensorBoard 日志、最佳 checkpoint；
- 验证集与测试集的 Recall@10/20/40/80、NDCG@10/20/40/80；
- 汇总表中按噪声比例排列的性能与相对 0 噪声退化幅度。

### 1.6 实现时必须锁定的细节

1. **取整规则**：比例 x 与用户交互数 n_u 的乘积未必为整数。实现前需统一明确使用 `floor`、`round`、`ceil`，以及是否保证 x>0 时交互数足够的用户至少替换 1 条；该规则必须写入日志和工程记录。
2. **候选边去重**：同一用户补入的 bundle 必须互不重复，且不得仍属于其原始训练集合 T_u。
3. **不修改原始数据**：所有噪声训练集必须输出到独立目录；原始 `datasets/` 永远保留为只读基准。
4. **验证/测试隔离风险**：当前任务的字面候选集合为“训练集中未交互过的 bundle”，即 B \ T_u。该集合可能包含 tune/test 正样本。若把这些 bundle 注入训练集，会造成验证/测试标签泄漏，并且被训练掩码遮蔽，导致评估不再严格有效。正式实现前必须确认候选集合究竟按字面使用 B \ T_u，还是采用更严格的 B \ (T_u ∪ V_u ∪ E_u) 以彻底避免泄漏；在未确认前，不擅自改变任务定义。
5. **可复现性**：噪声生成必须独立于模型训练随机性；推荐为每个“数据集 × 比例”固化一个噪声种子与生成结果，使 54 组实验可重复、可审计、可公平比较。
6. **运行隔离与可恢复性**：总控脚本应支持跳过已成功完成的实验、识别失败实验并单独重跑，避免服务器中断后重复全部 54 组训练。

### 1.7 服务器执行目标

服务器准备完成后，总控脚本应按如下逻辑工作：

1. 校验 Python/PyTorch/CUDA、TensorBoard、数据与外部 embedding 路径；
2. 为每个数据集和噪声比例生成或验证对应的独立噪声训练集；
3. 将对应噪声训练集提供给 CrossCBR、MultiCBR、ReCoBR；
4. 依次运行训练，记录状态；ReCoBR 在 NetEase/Youshu 使用 CBR 分支，在 iFashion 使用 DWT 分支；
5. 汇总所有结果，生成抗噪曲线和对比表所需的结构化结果文件；
6. 支持因服务器中断或单次异常而断点续跑。

当前尚未开发噪声生成器、总控脚本、结果汇总器，也未在本地或服务器启动任何训练。后续每次实现与方案决策均在本文件新增记录项。

## 2. 抗噪候选 bundle 范围确认（2026-10-13）

已确认：噪声替换时，不使用“全量 metadata 中所有 bundle”的候选空间；而是仅从**原始训练集内曾出现过**的 bundle 中抽样。

对数据集 d，定义：

- B_train：`user_bundle_train.txt` 中被任意用户交互过的全部 bundle ID 的集合；
- T_u：用户 u 在原始 `user_bundle_train.txt` 中的 bundle 集合；
- C_u = B_train \ T_u：用户 u 的随机替换候选集合。

因此，用户 u 被移除 m_u 条原始训练边后，应从 C_u 中不放回随机抽取 m_u 个 bundle 补入。候选判断始终基于**原始干净训练集**，而不是基于已经注入噪声后的临时训练图。

按当前确认的定义，不额外排除该用户的 tune/test 正样本；后续实现将严格遵循这一约定，并在每份噪声数据的元信息中记录候选集合定义。
