第四项：对比模型接入的第二种情况通用方案及搜参管理约定
时间：2026-10-25 00:45:24（北京时间，UTC+08:00）

一、适用范围与工作顺序
本方案适用于 DCBR、MultiCBR 及后续加入的各个对比模型在作者论文或开源项目未提供相关数据集配置时的参数搜索工作。
每个接入模型先完成第一种情况的工作，再开展第二种情况。第一种情况开发好的训练代码和配置体系应继续复用；第二种情况在模型配置文件中补充目标数据集的合理初始配置，再开展分轮参数搜索。
初始配置可参考作者已有配置、论文参数范围和目标数据集特点，明确其为搜索起点，不将经验设定值视为已验证的最优值。
本方案承接第三项的公平比较原则、公共数据与评测选模标准，以及 ReCoBR 和各模型 raw 目录保持不动的开发边界。

二、分轮搜参的组织方式
1. 一个模型在一个作者未提供配置的数据集上的搜参工作，可能需要多轮实验，每轮包含多个实验配置。
2. 具体依次搜索哪些参数、每轮取哪些值，由用户与助手结合对应模型、数据集及此前验证结果讨论决定。当前仅确定通用方案，不预先规定各模型的搜索顺序、范围和轮数。
3. 自动化脚本负责执行已安排的实验及管理记录；后续实验计划由双方根据具体情况制定。
4. 每次启动通过轮次 ID 指定本次运行集中配置文件中的哪一轮实验，并支持按实验 ID 指定重跑。
5. 参数和配置选择依据验证集，继续沿用共同的验证选模规则。测试指标可以保存，但不得用于调整搜索方向、选择配置或决定是否继续搜索。

三、文件职责与集中配置管理
各模型的相关开发文件放在各自目录下，raw 仅作原始实现参考。以下为文件职责，具体文件名、格式和实现组织方式留待后续确定：
1. 已有训练代码：读取一次实验的实际配置，完成训练、验证选模和结果保存，供两种情况共用。
2. 模型配置文件：保存各数据集的基础配置，第二种情况补入新数据集配置。
3. 集中搜参配置文件：供自动化脚本读取，集中保存各数据集、各轮及各实验的配置信息、识别信息、轮次 ID、实验 ID、备注和执行状态（包括是否成功）。脚本自动更新运行状态，同时保留实际执行历史。
4. 自动化脚本：读取指定轮次，组织实验执行、状态更新、结果检查与汇总。
5. 搜参结果 TXT：专门追加保存第二种情况的实验结果，与第一种情况的实验结果文档分开。
集中配置文件应能够明确区分不同数据集、轮次和实验。每次实际执行还应有独立标识，以区分重跑与失败重试，不覆盖旧执行结果。

四、自动化脚本的重要参考及能力要求
用户提供了另一个调参分支中已开发的串行 iFashion 自动化脚本，作为后续开发的重要参考。该脚本已考虑多种执行与记录因素，后续应完整研究其机制，并结合不同模型、数据集和集中配置管理需求进行适配，不直接沿用其中写死的特定数据集、参数字段或展示内容。
自动化脚本需要考虑以下能力：
1. 实验识别：数据集、轮次 ID、实验 ID、轮次备注、实验备注及每次执行的独立 ID。
2. 配置管理：基础配置与实验覆盖项、参数合法性检查、实际配置快照，以及配置和代码指纹。
3. 执行控制：串行运行、指定 GPU、跳过有效的历史成功实验、指定实验重跑和失败重试。
4. 中断处理：保存执行状态，识别未完成实验和遗留训练进程，避免重复启动同一轮或重复执行仍在运行的实验。
5. 控制台信息管理：清楚显示当前数据集和轮次、备注、GPU、计划及本次实验数量、跳过数量、当前实验、尝试次数，以及等待、运行、重试、成功、失败、中断等状态。
6. 时间统计：记录精确到秒且注明时区的开始和结束时间、单次尝试耗时、包含重试的总耗时；中断导致时间无法准确确定时，应明确说明。
7. 结果完整性检查：结合进程退出状态、训练结果、实际配置、最佳轮次、指标和检查点等确认实验是否完整成功，避免仅凭进程退出或文件存在就认定成功。
8. 历史与产物追溯：保存每次尝试的日志、失败原因、代码版本、源码摘要、实际配置、结果及产物位置，避免重跑覆盖历史。
9. 写入与并发管理：可靠保存状态，避免结果重复追加，并防止同一轮被多个控制进程重复执行。
失败重试次数、中断实验从头运行还是恢复训练等具体运行规则，后续再明确；当前不将参考脚本中的固定取值直接作为所有模型的最终规定。

五、成功状态、历史结果与搜参结果保存
1. 集中配置文件中的成功状态必须对应实际执行时的配置和代码。修改配置或代码后，不得仅因实验 ID 相同就沿用旧成功状态或直接跳过；旧执行记录仍需保留。
2. 搜参结果 TXT 按轮次和实验追加记录，至少包含轮次及实验标识、备注、状态、GPU、开始和结束时间、耗时、尝试次数、完整实际配置、代码版本与指纹、日志及检查点位置。
3. 成功实验保存 best_epoch（注明计数方式）、最佳验证选模分数，以及同一最佳检查点对应的完整验证集和测试集指标，不拼接不同轮次的指标。
4. 失败或中断的实验也应保留状态、原因及已有尝试记录，保证整个搜索过程可追溯。
5. 每轮配置、单次执行记录与轮次汇总应能相互对应，便于根据验证结果讨论下一轮实验。
6. 本项中的搜参配置状态更新与实验结果保存属于后续实验程序的职责；根目录工程记录.txt 仍严格按第一项规则维护，仅在用户明确要求时记录或修改。

十一、前后阶段依赖、选择依据与失效处理
1. 后4组通过 inherit_best 指定前5组候选和 validation_recall20_then_ndcg20。候选必须是同轮中已经声明的实验，不能引用自身、尚未声明的实验、重复候选或测试集选值规则，从结构上避免循环与未定义依赖。

十二、成功判定、重试、恢复和并发控制
1. 默认 --mode resume 跳过当前指纹下经复核的成功实验，补跑未完成或失效实验；--mode failed 仅选择当前指纹下最近失败的实验；--mode selected --only <实验ID...> 指定重跑；--mode all 重跑本轮全部。指定模式不会隐式补跑其他未选前置，缺少依赖时显示 BLOCKED；完成整条依赖优先使用默认恢复模式。
2. 成功判定同时检查进程退出、SUCCESS及completed状态、完整训练轮数、实际配置、数据集和运行标识、设备、源码与数据摘要、best epoch合法性、完整验证/测试指标、验证选模指标对应关系、配置快照、内部与外部结果 JSON 一致性，以及检查点等关键文件的存在、非空和摘要。
3. 代码、数据、配置、设备或选择来源改变后重新计算指纹，不仅凭历史 status 或文件存在跳过。检查点缺失或被更改时，旧 SUCCESS 映射为 INVALIDATED，默认恢复模式重新执行；当前控制器内对未变化文件复用复核结果以减少重复读取，重新启动仍重新核查。
4. 每次执行使用独立执行ID，每次尝试使用独立快照、日志和产物目录。失败重试最多3次，当前间隔5秒，旧失败原因保留。所有重试及中断后的新执行均从第1轮开始，不提供从旧检查点续训的命令。
5. 正常中断控制器时停止当前所属子进程并记录 INTERRUPTED。训练子进程返回中断码（包括130）同样停止本轮，不作为普通失败自动重试，避免人工停止后程序又启动训练。
6. 强制结束控制器后，恢复前核查遗留训练PID；进程可能仍在运行时阻止新训练，不自动结束其他进程。跨机器遗留 RUNNING 或PID重用等不能可靠判定的情形，需要先核查原服务器。
7. 子进程在PID写入历史后才放行训练；控制器若在启动与登记之间崩溃，未获放行的引导进程超时退出，避免无记录地进入CUDA训练。
8. 对集中计划和工作目录持有操作系统文件锁，对报告写入加锁；状态、JSON和汇总采用原子替换，减少重复控制、并发覆盖和半写入。运行期间发现人工编辑声明式计划会停止并保留历史，不静默覆盖用户的新计划。
9. 北京时间起止时间精确到秒，耗时使用单调时钟，总耗时包含重试与相关执行准备。强制中断后无法确定实际停止时刻时，标注恢复检测时间和耗时未知，不将检测时间冒充真实结束时间。

6. 两个数据集的lambda_0阶段均由100取得最高验证Recall@20，论文候选中的1、10尚未搜索，存在进一步向小核查的依据。不过当前证据较弱：NetEase由1000降到100仅从0.04882368956320974提高到0.04891799174130858，相对约0.19%，各中间候选不呈明显单调关系。Youshu当时的lambda_0比较则基于K=1、omega=0、tau=0.2等旧背景，不能直接外推到现配置。
7. NetEase的K=1优于全部更大的K候选，现有结果没有支持继续增大K的方向，也无正常更小的正整数K可搜。NetEase的tau=0.15位于当前网格内部；0.1与0.15结果较近，不具有与lambda_1相同强度的边界证据。omega及已搜索的Youshu gamma配比亦无明确的向外持续改善线索。

五、参数耦合与阶段搜索后的回查原则
1. 当前推荐训练目标由BPR、lambda_2控制的显式L2正则，以及lambda_1控制的对比学习项组成；对比项内部再由gamma_1、gamma_2加权视图间与视图内损失。DCBR/train.py保留作者这一计算关系，不能将这些系数视为互不影响。
2. NetEase最初搜索lambda_1时，lambda_2=1e-5、tau=0.2、lambda_0=1000；最终配置已经变为lambda_2=1e-7、tau=0.15、lambda_0=100。因此，旧结果中lambda_1=0.005优于0.01，不保证在最终背景下仍保持相同差距和排序；需要兼顾向小扩展与对邻近旧值的回查。
3. Youshu从K=1改为更大的K会改变UB视图以及相关对比信号，故温度、对比损失权重和扩散一致性约束的适合值也可能变化。先确定K，再在相同K下比较其他参数，比混用不同K的旧结果更有解释力。
4. 对于新完整基准下的单参数比较，只有除当前搜索项外全部配置、种子、预算、数据和评测协议一致的历史实验才能直接作为对照；仅有相同参数值不代表可复用。例如新K下回查tau=0.1，不能直接用旧K=1的tau_010成绩代替。
5. 顺序搜索是控制成本的方法，不是一次扫描即可保证全局最优。后期关键设置发生较大变化后，应视结果有针对性地回查早期参数，不能无依据要求所有参数全组合穷举，也不能反过来宣称剩余设置都不重要。

六、本次讨论提出的补搜建议及来源
1. 优先级：NetEase的lambda_1、lambda_2最值得下探；Youshu先补K上界确认，再视结果研究温度。lambda_0的小值补充有论文依据，但现有收益及趋势较弱，优先级相对靠后。
2. NetEase建议以当前优胜完整配置为对照，比较lambda_1=0.001、0.002、0.01：前两个用于向小探索，0.01用于回查后期配置变化后的邻近旧值；当前0.005继续作为对照，不强制从新值中选一个。上述比较必须在同一完整背景下重新进行，不直接使用旧lambda1_001成绩。
3. NetEase选定lambda_1后，再考虑lambda_2=1e-8、1e-9，保留此前完整优胜配置为对照；逐阶段继承全部已确定参数，只改当前参数。此处属于研究建议，具体范围与执行安排尚未转为新轮次计划。
4. Youshu建议以K=11为对照，向大补K=13、17、21，作为逐步扩展而非无依据跳到很大K的确认点。这些取值是本次讨论提出的工程补充，不是论文给定范围，亦不是已经运行的结果。

六、论文依据、搜索顺序与选优协议
1. 已核对ReCoBR.pdf的方法、参数设置及敏感性分析。论文重点分析K、扩散噪声上限、SetLoss权重、融合前对比权重和融合后对比权重；当前融合前对比关闭，不把相关字段当搜索项。

3. 单次训练内，只有当前验证Recall@20和NDCG@20同时严格超过同一个已保存检查点的对应值，才更新best epoch和检查点。按test_interval=5执行评测，不在未到间隔的最后epoch额外选择模型；150轮预算内最后一次计划评测为第150轮。
