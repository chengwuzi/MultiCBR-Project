第四项：对比模型接入的第二种情况通用方案及搜参管理约定
时间：2026-10-25 00:45:24（北京时间，UTC+08:00）

一、适用范围与工作顺序
本方案适用于 DCBR、MultiCBR 及后续加入的各个对比模型在作者论文或开源项目未提供相关数据集配置时的参数搜索工作。
每个接入模型先完成第一种情况的工作，再开展第二种情况。第一种情况开发好的训练代码和配置体系应继续复用；第二种情况在模型配置文件中补充目标数据集的合理初始配置，再开展分轮参数搜索。
初始配置可参考作者已有配置、论文参数范围和目标数据集特点，明确其为搜索起点，不将经验设定值视为已验证的最优值。
本方案承接第三项的公平比较原则、公共数据与评测选模标准，以及 ReCoBR 和各模型 raw 目录保持不动的开发边界。

二、分轮搜参的组织方式
1. 一个模型在一个作者未提供配置的数据集上的搜参工作，可能需要多轮实验，每轮包含多个实验配置。
2. 具体依次搜索哪些参数、每轮取哪些值，由用户与助手结合对应模型、数据集及此前验证结果讨论决定。当前仅确定通用方案，不预先规定各模型的搜索顺序、范围和轮数。
3. 自动化脚本负责执行已安排的实验及管理记录；后续实验计划由双方根据具体情况制定。
4. 每次启动通过轮次 ID 指定本次运行集中配置文件中的哪一轮实验，并支持按实验 ID 指定重跑。
5. 参数和配置选择依据验证集，继续沿用共同的验证选模规则。测试指标可以保存，但不得用于调整搜索方向、选择配置或决定是否继续搜索。

三、文件职责与集中配置管理
各模型的相关开发文件放在各自目录下，raw 仅作原始实现参考。以下为文件职责，具体文件名、格式和实现组织方式留待后续确定：
1. 已有训练代码：读取一次实验的实际配置，完成训练、验证选模和结果保存，供两种情况共用。
2. 模型配置文件：保存各数据集的基础配置，第二种情况补入新数据集配置。
3. 集中搜参配置文件：供自动化脚本读取，集中保存各数据集、各轮及各实验的配置信息、识别信息、轮次 ID、实验 ID、备注和执行状态（包括是否成功）。脚本自动更新运行状态，同时保留实际执行历史。
4. 自动化脚本：读取指定轮次，组织实验执行、状态更新、结果检查与汇总。
5. 搜参结果 TXT：专门追加保存第二种情况的实验结果，与第一种情况的实验结果文档分开。
集中配置文件应能够明确区分不同数据集、轮次和实验。每次实际执行还应有独立标识，以区分重跑与失败重试，不覆盖旧执行结果。

四、自动化脚本的重要参考及能力要求
用户提供了另一个调参分支中已开发的串行 iFashion 自动化脚本，作为后续开发的重要参考。该脚本已考虑多种执行与记录因素，后续应完整研究其机制，并结合不同模型、数据集和集中配置管理需求进行适配，不直接沿用其中写死的特定数据集、参数字段或展示内容。
自动化脚本需要考虑以下能力：
1. 实验识别：数据集、轮次 ID、实验 ID、轮次备注、实验备注及每次执行的独立 ID。
2. 配置管理：基础配置与实验覆盖项、参数合法性检查、实际配置快照，以及配置和代码指纹。
3. 执行控制：串行运行、指定 GPU、跳过有效的历史成功实验、指定实验重跑和失败重试。
4. 中断处理：保存执行状态，识别未完成实验和遗留训练进程，避免重复启动同一轮或重复执行仍在运行的实验。
5. 控制台信息管理：清楚显示当前数据集和轮次、备注、GPU、计划及本次实验数量、跳过数量、当前实验、尝试次数，以及等待、运行、重试、成功、失败、中断等状态。
6. 时间统计：记录精确到秒且注明时区的开始和结束时间、单次尝试耗时、包含重试的总耗时；中断导致时间无法准确确定时，应明确说明。
7. 结果完整性检查：结合进程退出状态、训练结果、实际配置、最佳轮次、指标和检查点等确认实验是否完整成功，避免仅凭进程退出或文件存在就认定成功。
8. 历史与产物追溯：保存每次尝试的日志、失败原因、代码版本、源码摘要、实际配置、结果及产物位置，避免重跑覆盖历史。
9. 写入与并发管理：可靠保存状态，避免结果重复追加，并防止同一轮被多个控制进程重复执行。
失败重试次数、中断实验从头运行还是恢复训练等具体运行规则，后续再明确；当前不将参考脚本中的固定取值直接作为所有模型的最终规定。

五、成功状态、历史结果与搜参结果保存
1. 集中配置文件中的成功状态必须对应实际执行时的配置和代码。修改配置或代码后，不得仅因实验 ID 相同就沿用旧成功状态或直接跳过；旧执行记录仍需保留。
2. 搜参结果 TXT 按轮次和实验追加记录，至少包含轮次及实验标识、备注、状态、GPU、开始和结束时间、耗时、尝试次数、完整实际配置、代码版本与指纹、日志及检查点位置。
3. 成功实验保存 best_epoch（注明计数方式）、最佳验证选模分数，以及同一最佳检查点对应的完整验证集和测试集指标，不拼接不同轮次的指标。
4. 失败或中断的实验也应保留状态、原因及已有尝试记录，保证整个搜索过程可追溯。
5. 每轮配置、单次执行记录与轮次汇总应能相互对应，便于根据验证结果讨论下一轮实验。
6. 本项中的搜参配置状态更新与实验结果保存属于后续实验程序的职责；根目录工程记录.txt 仍严格按第一项规则维护，仅在用户明确要求时记录或修改。

4. 必须等待前5组全部有效成功，再按已确认的跨配置规则选择优胜配置；初始对照也参与选择，因此允许保留 lambda_1=0.01，不强行从另外4个值中选择。
5. 第6至9组继承上述优胜实验的完整模型配置，仅覆盖 lambda_0，分别搜索相对初始 lambda_0=1000 的两个小值、两个大值：
   lambda0_0100：lambda_0=100，为初始值的1/10。
   lambda0_0500：lambda_0=500，为初始值的1/2。
   lambda0_2000：lambda_0=2000，为初始值的2倍。
   lambda0_10000：lambda_0=10000，为初始值的10倍。
6. 用户已明确确认以上取值。lambda_1=0.002/0.005、lambda_0=500/2000 是本工程补充搜索点；lambda_1=0.02/0.05、lambda_0=100/10000 是论文候选值。初始对照中的 lambda_1=0.01、lambda_0=1000 同样在论文候选集中。
7. 本轮采用自动选定并继续执行，用户无需在前5组完成后手动填入 lambda_1。程序只能按已确认的规则比较已安排的候选，不自行增加实验、改范围或决定下一轮搜索方向。

八、必须分清两层选择规则
1. 单次实验内部的 best epoch：继续沿用第五项已经确定的统一协议。只有当前验证 Recall@20 和 NDCG@20 都严格超过此前保存检查点的对应值，才更新检查点；相等不更新，两项基准一起来自同一已保存检查点。该规则本次没有改动，仍适用于 ReCoBR 和接入模型的统一评测流程。
2. 本轮不同实验配置之间的自动取舍：用户明确确认 validation_recall20_then_ndcg20。先比较每个实验已选 best epoch 的验证 Recall@20，完全相同再比较验证 NDCG@20；两项都完全相同，则保留集中配置中声明顺序在前的实验。
3. 跨配置比较使用 JSON 中保存的完整精度数值，不按 TXT 展示的四舍五入值判断平局，不将各指标相加，也不读取测试指标决定优胜。后4组继承的是该规则选中的实际配置，不是由测试集或单个训练损失决定的参数。
4. 本轮全部9组有效成功后，轮次汇总使用同一跨配置规则给出本轮最佳实验；任一组缺失、失败、中断或结果失效时，汇总明确标为未完成，不给出完整轮次的最佳配置。
5. 论文比较和后续模型接入应显式说明“训练内选检查点”与“训练间选超参数配置”的区别，不能因本轮新增跨配置规则就默默改变公共 best epoch 协议。其他模型复用自动选择机制时，仍应明确记录采用的取舍规则。

九、文件职责及本次代码开发
1. DCBR/train.py：继续承担一次实验的训练、评测、best epoch 和产物保存。适配 first/second 实验类别，Youshu 默认归入第二种情况；自动入口显式传入 second。第一种情况默认写 DCBR/实验记录.txt，第二种情况默认写 DCBR/搜参结果.txt，自动批量执行时各次尝试先写日志目录中的独立训练TXT，由控制器另写一份执行汇总。
2. DCBR/config.yaml：保留原 iFashion 项，新增 Youshu 迁移初始配置及90轮预算。
3. DCBR/搜参配置.yaml：集中保存多数据集、多轮次及各实验的声明、ID、备注、参数覆盖和程序维护的执行状态；当前已填入 youshu_round_01 的9组及其依赖。
4. DCBR/run_experiments.py：读取集中配置并执行指定轮次，支持前置结果选值、独立子进程训练、GPU指定、串行执行、重试、恢复、重跑、结果复核、状态同步及轮次汇总。控制进程不导入 torch 或模型，使用当前 Python 环境启动训练子进程。
5. DCBR/搜参结果.txt：第二种情况的正式可读汇总，与情况一记录分开。截至本项写入时仍为空，未混入开发测试结果。
6. DCBR/test_automation.py：新增自动化、依赖、失败、中断恢复和结果完整性测试；DCBR/test_reproduction.py 保留原始数值与情况一回归测试。DCBR/README.md 同步说明来源、规则、运行方式、依赖与限制；.gitignore 补充忽略 DCBR 顶层运行锁文件。
7. 训练结果 JSON 新增完整完成轮数和检查点、检查点配置、实际配置快照的 SHA256，供自动化复核。已有 iFashion 结果保持原样，不回填或改写历史字段。

十、集中配置、覆盖规则与运行参数
1. 生效顺序为“数据集基础配置→本轮公共覆盖→单个实验覆盖”；依赖实验在前置结果就绪后继承优胜实验的完整模型配置，再施加该实验的覆盖。实际执行配置另存快照，不能仅靠以后可能改变的基础配置路径追溯。
2. 轮次ID在集中配置中唯一，实验ID在轮次内唯一，使用1至64位英文字母、数字、下划线或连字符；轮次和每个实验均需备注。程序拒绝未知字段、重复 YAML 键及非法依赖。
3. seed、epochs、数据路径、批大小、嵌入维数、传播层数等公共设置在轮次层面指定，不能被单个实验偷偷覆盖；topk、test_interval、neg_num 保持基础配置的公共协议。字段可被程序接受不等于研究上已经批准将其作为搜索对象。
4. 集中配置的 defaults 当前为 GPU='0'、device=cuda、max_attempts=3、retry_delay_seconds=5、console_interval_seconds=30、stream_output=false。最多3次包含首次尝试；以上是本工程当前可配置运行设置，不是论文统一要求。
5. 默认每30秒显示轮次、备注、计划/本次/跳过数量、当前实验、尝试、等待、运行、重试、成功、失败、中断及前置等待状态，并显示最近训练输出。完整输出始终保存在独立日志；可开启 stream_output 实时转发，自动入口关闭批次进度条以减少刷屏。
6. 配置中各路径相对项目根目录解释，显式 --plan 路径相对当前工作目录；默认计划定位在 DCBR 目录，从根目录或 DCBR 内启动均可。--gpu、--device 可覆盖执行设备，训练子进程沿用当前解释器，不自动切换 Conda 环境。
7. 程序维护的 status、success、fingerprint、execution_ids、resolved_config、dependency_selection、blocked_by 均为历史映射或解析结果，不能手工填 success=true 代替运行。集中配置更新会重新序列化 YAML，研究说明应写入 note 字段，不能依赖普通注释长期保存。

十一、前后阶段依赖、选择依据与失效处理
1. 后4组通过 inherit_best 指定前5组候选和 validation_recall20_then_ndcg20。候选必须是同轮中已经声明的实验，不能引用自身、尚未声明的实验、重复候选或测试集选值规则，从结构上避免循环与未定义依赖。
2. 全部前置候选必须成功并通过配置、数据、源码、指标及产物检查。任一前置失败、未完成或失效时，后续为 BLOCKED，不使用部分候选选值，也不以初始 lambda_1 冒充已经选出的值。首次预览中后4组显示 BLOCKED 是正常的前置等待状态。
3. 前置未就绪时，后续实际 config 和 fingerprint 不生成；程序使用内部 template_config 检查已确定的覆盖值，但检查模板不会发布或执行为实际配置。前置优胜确定后，再校验继承得到的完整实际配置，才启动训练。
4. dependency_selection 保留比较规则、平局规则、各候选实验ID、执行ID、配置指纹和验证指标，以及优胜实验和执行ID。选择依据同时进入集中配置、执行历史、单次 execution.json 和 TXT 汇总，能够追踪后续配置究竟继承了哪次运行。
5. 后续实验指纹包含前置选择依据，包括全部候选的执行版本。前置被重跑后，即使优胜 lambda_1 数值未变，选择来源已改变，也要重新核查后续状态，不能仅按相同实验ID沿用旧成功结果。旧执行与产物仍保留。

十二、成功判定、重试、恢复和并发控制
1. 默认 --mode resume 跳过当前指纹下经复核的成功实验，补跑未完成或失效实验；--mode failed 仅选择当前指纹下最近失败的实验；--mode selected --only <实验ID...> 指定重跑；--mode all 重跑本轮全部。指定模式不会隐式补跑其他未选前置，缺少依赖时显示 BLOCKED；完成整条依赖优先使用默认恢复模式。
2. 成功判定同时检查进程退出、SUCCESS及completed状态、完整训练轮数、实际配置、数据集和运行标识、设备、源码与数据摘要、best epoch合法性、完整验证/测试指标、验证选模指标对应关系、配置快照、内部与外部结果 JSON 一致性，以及检查点等关键文件的存在、非空和摘要。
3. 代码、数据、配置、设备或选择来源改变后重新计算指纹，不仅凭历史 status 或文件存在跳过。检查点缺失或被更改时，旧 SUCCESS 映射为 INVALIDATED，默认恢复模式重新执行；当前控制器内对未变化文件复用复核结果以减少重复读取，重新启动仍重新核查。
4. 每次执行使用独立执行ID，每次尝试使用独立快照、日志和产物目录。失败重试最多3次，当前间隔5秒，旧失败原因保留。所有重试及中断后的新执行均从第1轮开始，不提供从旧检查点续训的命令。
5. 正常中断控制器时停止当前所属子进程并记录 INTERRUPTED。训练子进程返回中断码（包括130）同样停止本轮，不作为普通失败自动重试，避免人工停止后程序又启动训练。
6. 强制结束控制器后，恢复前核查遗留训练PID；进程可能仍在运行时阻止新训练，不自动结束其他进程。跨机器遗留 RUNNING 或PID重用等不能可靠判定的情形，需要先核查原服务器。
7. 子进程在PID写入历史后才放行训练；控制器若在启动与登记之间崩溃，未获放行的引导进程超时退出，避免无记录地进入CUDA训练。
8. 对集中计划和工作目录持有操作系统文件锁，对报告写入加锁；状态、JSON和汇总采用原子替换，减少重复控制、并发覆盖和半写入。运行期间发现人工编辑声明式计划会停止并保留历史，不静默覆盖用户的新计划。
9. 北京时间起止时间精确到秒，耗时使用单调时钟，总耗时包含重试与相关执行准备。强制中断后无法确定实际停止时刻时，标注恢复检测时间和耗时未知，不将检测时间冒充真实结束时间。

十三、结果与产物追溯
1. 默认工作目录为 DCBR/log/tuning；全局 history.json 保存跨轮次执行历史，是恢复依据。集中 YAML 的状态只是历史在当前配置与指纹下的映射，两者应能够相互核查。
2. 每次执行目录为 DCBR/log/tuning/<数据集>/<轮次ID>/<实验ID>/<执行ID>/，保存训练器和控制器源码快照、execution.json，以及各次尝试的配置、stdout、训练TXT、外部结果JSON和独立训练产物目录。
3. 训练产物继续包含 training.log、config.yaml、TensorBoard、best.pt、best_config.json、result.json；检查点内容沿用已有模型、去噪网络、扩散状态、重建图及优化器状态。保留检查点重评测能力，数据摘要应与训练一致。
4. DCBR/搜参结果.txt 按执行追加完整段，包含轮次/实验/执行标识及备注、状态、GPU和设备、起止时间、含重试总耗时、各次尝试及原因、完整实际配置、代码版本、源码/数据摘要、依赖选择、最佳轮次与同一检查点的各Top-K验证/测试指标及产物路径。各指标不能跨轮拼接。
5. 控制器正常结束本轮或本次选定实验后，写入 DCBR/log/tuning/Youshu/youshu_round_01/round_summary.json，并向搜参TXT追加对应轮次汇总。仅9组全部有效成功时生成本轮最佳配置，否则明确记录未完成；通过汇总标识避免恢复时重复追加相同内容。
6. 训练日志、历史及模型产物位于已有忽略目录，正式TXT汇总和集中计划可随项目同步；仅同步 success 字段不能替代同步并核查对应历史和产物。第一种情况TXT、第二种情况TXT、根目录工程记录分别承担不同职责，不相互覆盖。

十五、运行方式与后续模型可复用的结论
1. 在项目根目录检查基础配置：python DCBR/train.py -d Youshu --check-config。
2. 列出集中计划：python DCBR/run_experiments.py --list。
3. 预览本轮：python DCBR/run_experiments.py --round youshu_round_01 --dry-run。
4. 在用户已准备好的CUDA环境正式执行：python -u DCBR/run_experiments.py --round youshu_round_01 -g 0。默认恢复同一命令会核查并跳过有效成功实验，继续剩余计划。
5. 后续模型可参照本次流程：先完成作者已有数据集接入，再选择相近作者配置作为新数据集起点；先吃透论文与实现，区分固定设置、可调超参数、运行参数和核心机制；说明每个搜索点来源，经讨论确定后再执行。
6. 参数搜索应说明初始对照、轮次预算及不变条件，并考虑组合规模和参数相互作用。本次 DCBR 采用的先粗后细及分阶段顺序可供研究参考；其他模型是否采用同样方式、先搜索哪些参数、如何联合或细化搜索，须结合对应模型及其论文另行确定。对于采用依赖搜索的计划，应保存完整选择依据和实际配置，并在前置失败或来源改变时阻止错误沿用。
7. 自动化应保证可核查、可恢复、可追溯，不能代替研究判断；单次运行成功、局部验证提升、完成一轮搜索或通过开发测试，都不单独证明得到全局最优，也不意味着全部公平性问题已解决。
8. 公共数据、评测、训练内选模保持约定；跨配置规则另行显式说明，所有选择只依据验证集。具体候选集、调参顺序、轮数、重试设置等应结合新模型和数据集确定，不把本轮数字机械套用到其他任务。
9. 后续若出现统一框架要求与模型机制之间影响公平性的实质冲突，继续先说明影响、依据及处理选项，与用户讨论确定后执行并留痕。各模型获得的搜索机会及实际预算也需在最终比较中如实说明。
