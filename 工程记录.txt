## 1. 抗噪实验任务背景与项目现状（2026-10-13）

### 1.1 总目标

后续将在实验室服务器上完成三个捆绑推荐模型在三个数据集上的抗噪实验。实验要检验：当训练期用户—捆绑（User-Bundle，UB）交互被人为注入不同程度的随机错误边后，各模型的推荐性能如何变化，以及 ReCoBR 相对两个已有论文模型是否具有更好的抗噪性。

本地机器不用于训练；本地只承担代码阅读、实现、配置整理和脚本准备。最终期望的交付形态是：项目同步至服务器后，只需执行一条总控命令，脚本即可自动生成噪声数据、依次运行全部实验、保存配置与日志，并汇总结果。

### 1.2 三个模型的归属与代码位置

1. **CrossCBR**：其他论文的公开基线模型，目录为 `CrossCBR/`。
   - 采用 UI（用户—物品）与 UB（用户—捆绑）两个视图。
   - 在两个视图上进行图传播，以 BPR 为主损失，并使用跨视图对比学习。
   - 入口：`CrossCBR/train.py`；模型：`CrossCBR/models/CrossCBR.py`。

2. **MultiCBR**：其他论文的公开基线模型，目录为 `MultiCBR/`。
   - 采用 UB、UI、BI（捆绑—物品）三个视图。
   - 对三张二部图分别传播、聚合，再使用配置中的模态与层权重融合。
   - 入口：`MultiCBR/train.py`；模型：`MultiCBR/models/MultiCBR.py`。

3. **ReCoBR**：本项目自己的方法，位于仓库根目录。
   - 源码内部的 CBR 分支类名为 `AnchorViewBundleNet`，DWT 分支类名为 `DWT`；后续报告、脚本、日志目录和实验表格统一使用名称 **ReCoBR**。
   - 模块一：利用外部预训练 UB 表示，对用户已观测 bundle 集合进行潜在扩散净化，并只在该用户原始已观测 UB 边中筛选 Top-K 高置信边，得到训练期净化 UB 图。
   - 模块二：以 UB 为锚点，在多视图融合前对齐 UB—UI 和 UB—BI 的用户侧与 bundle 侧表示。
   - 当前默认配置：NetEase、Youshu 使用 CBR 分支；iFashion 使用 DWT 分支。DWT 在最终打分时融合 UI、BI 表示，UB 视图主要服务训练期结构与对比约束。
   - 入口：`train.py`；模型：`models/model.py`；配置：`config.yaml`。

### 1.3 数据集与数据格式

三个数据集均使用整数 ID，规模如下：

| 数据集 | 用户数 | Bundle 数 | Item 数 | 原始训练 UB 边数 |
| --- | ---: | ---: | ---: | ---: |
| Youshu | 8,039 | 4,771 | 32,770 | 34,416 |
| NetEase | 18,528 | 22,864 | 123,628 | 217,864 |
| iFashion | 53,897 | 27,694 | 42,563 | 1,213,676 |

每个数据集包含：

- `user_bundle_train.txt`：本次抗噪实验唯一允许改写逻辑的数据源，即训练 UB 边；
- `user_bundle_tune.txt`、`user_bundle_test.txt`：验证与测试标签，原则上保持原样；
- `user_item.txt`：UI 图，保持原样；
- `bundle_item.txt`：BI 图，保持原样；
- `*_data_size.txt`：用户、bundle、item 总数，保持原样；
- iFashion 另有原始字符串 ID 映射 JSON 文件，保持原样。

根目录 `datasets/` 与 `MultiCBR/datasets/` 的同名数据内容已经核对一致。CrossCBR 自带 `CrossCBR/dataset.tgz`，服务器运行前需要在 `CrossCBR/` 下解压为其自己的 `datasets/` 目录。

### 1.4 抗噪定义（当前任务的字面实现目标）

对每个模型、每个数据集、每个噪声比例 x，构造一份新的训练 UB 文件。噪声比例集合固定为：

`0, 0.05, 0.10, 0.15, 0.20, 0.25`

对任意用户 u，设其原始训练交互集合为 T_u，交互数为 n_u：

1. 按比例 x 从 T_u 中随机、不放回地选择 m_u 条已有训练交互作为被替换边；
2. 从该用户在训练集中**未交互过**的 bundle 中随机、不放回地抽取 m_u 个 bundle；
3. 用新抽到的 m_u 条 UB 边替换被移除的 m_u 条边。

例如，x=0.50 且某用户有 20 条训练 UB 交互时，随机移除其中 10 条，并随机补入 10 条该用户原训练集中没有交互过的 bundle。替换后每位用户的训练 UB 度数保持不变，整份训练图的总边数也保持不变；变化只来自正确边被随机错误边替代。

噪声比例为 0 时必须严格等于原始训练数据，作为无噪声基线。

### 1.5 实验矩阵与公平性原则

实验总量为：3 个模型 × 3 个数据集 × 6 个噪声比例 = **54 组正式训练实验**。

对于同一个“数据集 × 噪声比例”，三个模型必须使用同一份生成后的 UB 训练边，或至少使用同一个固定随机种子和完全相同的生成算法，以确保模型间差异来自模型本身，而不是不同的噪声采样结果。

每一组实验应至少保存：

- 模型名、数据集、噪声比例、数据噪声随机种子、训练随机种子；
- 原始/替换后的边数、受影响用户数、每用户替换数统计；
- 实际运行配置快照；
- 完整标准输出日志、TensorBoard 日志、最佳 checkpoint；
- 验证集与测试集的 Recall@10/20/40/80、NDCG@10/20/40/80；
- 汇总表中按噪声比例排列的性能与相对 0 噪声退化幅度。

### 1.6 实现时必须锁定的细节

1. **取整规则**：比例 x 与用户交互数 n_u 的乘积未必为整数。实现前需统一明确使用 `floor`、`round`、`ceil`，以及是否保证 x>0 时交互数足够的用户至少替换 1 条；该规则必须写入日志和工程记录。
2. **候选边去重**：同一用户补入的 bundle 必须互不重复，且不得仍属于其原始训练集合 T_u。
3. **不修改原始数据**：所有噪声训练集必须输出到独立目录；原始 `datasets/` 永远保留为只读基准。
4. **验证/测试隔离风险**：当前任务的字面候选集合为“训练集中未交互过的 bundle”，即 B \ T_u。该集合可能包含 tune/test 正样本。若把这些 bundle 注入训练集，会造成验证/测试标签泄漏，并且被训练掩码遮蔽，导致评估不再严格有效。正式实现前必须确认候选集合究竟按字面使用 B \ T_u，还是采用更严格的 B \ (T_u ∪ V_u ∪ E_u) 以彻底避免泄漏；在未确认前，不擅自改变任务定义。
5. **可复现性**：噪声生成必须独立于模型训练随机性；推荐为每个“数据集 × 比例”固化一个噪声种子与生成结果，使 54 组实验可重复、可审计、可公平比较。
6. **运行隔离与可恢复性**：总控脚本应支持跳过已成功完成的实验、识别失败实验并单独重跑，避免服务器中断后重复全部 54 组训练。

### 1.7 服务器执行目标

服务器准备完成后，总控脚本应按如下逻辑工作：

1. 校验 Python/PyTorch/CUDA、TensorBoard、数据与外部 embedding 路径；
2. 为每个数据集和噪声比例生成或验证对应的独立噪声训练集；
3. 将对应噪声训练集提供给 CrossCBR、MultiCBR、ReCoBR；
4. 依次运行训练，记录状态；ReCoBR 在 NetEase/Youshu 使用 CBR 分支，在 iFashion 使用 DWT 分支；
5. 汇总所有结果，生成抗噪曲线和对比表所需的结构化结果文件；
6. 支持因服务器中断或单次异常而断点续跑。

当前尚未开发噪声生成器、总控脚本、结果汇总器，也未在本地或服务器启动任何训练。后续每次实现与方案决策均在本文件新增记录项。

## 2. 抗噪候选 bundle 范围确认（2026-10-13）

已确认：噪声替换时，不使用“全量 metadata 中所有 bundle”的候选空间；而是仅从**原始训练集内曾出现过**的 bundle 中抽样。

对数据集 d，定义：

- B_train：`user_bundle_train.txt` 中被任意用户交互过的全部 bundle ID 的集合；
- T_u：用户 u 在原始 `user_bundle_train.txt` 中的 bundle 集合；
- C_u = B_train \ T_u：用户 u 的随机替换候选集合。

因此，用户 u 被移除 m_u 条原始训练边后，应从 C_u 中不放回随机抽取 m_u 个 bundle 补入。候选判断始终基于**原始干净训练集**，而不是基于已经注入噪声后的临时训练图。

按当前确认的定义，不额外排除该用户的 tune/test 正样本；后续实现将严格遵循这一约定，并在每份噪声数据的元信息中记录候选集合定义。

## 5. 按用户注噪数量的随机取整规则（2026-10-13）

对于噪声比例 x 和用户 u 的原始训练 UB 交互数 n_u，注噪数量定义为：

`m_u = floor(x * n_u) + Bernoulli(frac(x * n_u))`

其中 `frac` 为小数部分，Bernoulli 的成功概率等于该小数部分。即采用随机取整：

- 若 `x * n_u` 是整数，直接替换该整数数量；
- 若 `x * n_u = 0.35`，则以 35% 概率替换 1 条、65% 概率替换 0 条；
- 若 `x * n_u = 0.70`，则以 70% 概率替换 1 条、30% 概率替换 0 条。

该规则使每个用户的期望替换数量严格为 `x * n_u`，全数据集的期望噪声比例为 x；同时不强制低交互用户在每个非零比例下都至少替换一条，避免例如只有 1 条交互的用户在 5% 噪声下被必然 100% 污染。噪声生成器会使用固定种子，并记录每个数据集/比例的实际替换边数与实际噪声比例。

## 6. 注噪数量取整规则修订：不足 1 条不替换（2026-10-13）

根据任务要求，记录 5 中的随机取整方案不再采用。正式实现统一使用向下取整：

`m_u = floor(x * n_u)`

其中 x 为噪声比例，n_u 为用户 u 在原始训练集中的 UB 交互数。

因此，当 `x * n_u < 1` 时，`m_u = 0`，该用户在该噪声比例下不进行替换。例如：

- 用户有 7 条训练 UB 边、x=0.05，`floor(0.35)=0`，不替换；
- 用户有 20 条训练 UB 边、x=0.05，`floor(1.00)=1`，替换 1 条；
- 用户有 14 条训练 UB 边、x=0.10，`floor(1.40)=1`，替换 1 条。

这种规则意味着实际全局替换比例通常会略低于设定比例 x，尤其是在低交互用户占比较高的 Youshu 数据集上。总控脚本必须记录每个数据集/比例实际替换的 UB 边数及实际噪声比例，以便实验结果解释。

## 9. 54 组实验容错、续跑与执行顺序增强（2026-10-14）

根据实验保障要求，已升级 `noise_benchmark.py` 与 `抗噪实验使用说明.md`。

### 容错与续跑规则

1. 默认每组实验有 1 次首次启动与 3 次自动重试机会，即最多实际启动 4 次；可用 `--max-retries N` 调整重试次数。
2. 每一次尝试分别保存在 `runs/<experiment-id>/attempt_01/`、`attempt_02/` 等目录，包含独立的 `stdout.log`、`command.json`、开始/结束时间、返回码、失败原因和已解析指标，绝不覆盖此前日志。
3. 每次启动子训练进程前，控制器会先把 `running` 状态及本次尝试写入 `benchmark_manifest.json`。因此总控或服务器异常中断后，重新执行相同命令会跳过 `succeeded`，从剩余尝试次数继续未完成任务；已写入但因中断未结束的 `running` 尝试计为已消耗的一次机会。
4. 当一个实验全部尝试失败后，状态设为 `exhausted`，明确记录且自动跳过，后续实验照常进行。常规续跑也会跳过 `exhausted`；仅在人工确认需要后，才可通过 `--rerun-exhausted` 开启一轮新的重试预算。

### 执行顺序与结果精简

默认外层循环已调整为数据集优先：完整完成 Youshu 的 18 组后，再完成 iFashion 的 18 组，最后完成 NetEase 的 18 组；每个数据集内部顺序为 CrossCBR、MultiCBR、ReCoBR，且每个模型依次完成 6 个噪声比例。

指标结果只写入一个 `results_summary.csv`：一行对应一组实验，字段包含任务状态、尝试次数、失败原因、实际噪声比例和各 Top-K 的 Recall/NDCG 及相对 0 噪声变化。`benchmark_manifest.json` 只承担断点续跑与审计状态，不作为额外结果表。

### 已完成验证

- 使用故意不存在的 Python 启动器进行无训练故障演练：同一 CrossCBR/Youshu 任务依次失败 4 次，分别留下 4 份日志，最终正确标记为 `exhausted`；再次运行时正确跳过，未再启动子进程；CSV 仅保留一份且有一行对应此任务。
- 使用三模型、三数据集、0 噪声的 `--dry-run` 预演，确认实际命令顺序为 Youshu 的 CrossCBR→MultiCBR→ReCoBR、iFashion 的 CrossCBR→MultiCBR→ReCoBR、NetEase 的 CrossCBR→MultiCBR→ReCoBR；未启动本地模型训练。

## 10. 中断后残留训练进程的重复启动保护（2026-10-14）

进一步考虑“总控进程意外中断、但子训练进程仍在 GPU 上继续运行”的情况。现在总控在成功启动每次训练子进程后，会立即把其 PID 写入该次尝试的 `benchmark_manifest.json` 记录。恢复执行前会检查所有遗留 `running` 尝试：若其中记录的 PID 在本机仍存活，总控会停止并输出等待提示，不会重复拉起同一实验或与其争用 GPU；待该进程结束后重新执行原命令即可继续。PID 存活检测已完成无训练单元验证。

## 11. PID 状态持久化失败的清理保护（2026-10-14）

补充处理极端边界：若训练子进程已经创建，但写入其 PID 到状态清单时发生磁盘/文件 I/O 异常，总控会立即终止刚创建的子进程，并将此次尝试按失败记录，而不是遗留一个无 PID、无法安全恢复的 GPU 任务。已用短时无训练子进程模拟状态写入失败，确认该子进程会被取消并返回可记录的失败状态。

## 12. 正式 54 组实验前的三模型兼容性冒烟测试（2026-10-14）

为处理 CrossCBR、MultiCBR、ReCoBR 来自不同项目所带来的依赖、CUDA、接口和数据格式兼容性风险，已在 `noise_benchmark.py` 中加入强制前置兼容性关卡。

### 测试范围与执行规则

1. 正式执行 `python noise_benchmark.py run --gpu 0` 时，先按 CrossCBR→MultiCBR→ReCoBR 的顺序，仅在 Youshu 上执行三次兼容性冒烟测试；三者全部通过后才会生成并启动任何正式 54 组训练任务。
2. 每次测试使用对应模型的原始 Youshu 配置和同一份 0 噪声训练 UB 文件，但以 `--smoke-test` 限制为：1 个训练 batch、1 个验证 batch、1 个测试 batch、1 次 checkpoint/配置保存。测试仍真实覆盖导入依赖、CUDA、数据加载、图构建、模型前向/反向、优化、评估及文件写入。
3. 三个训练入口均新增 `--smoke-test`。ReCoBR 的 Youshu 测试同时会进入已启用的模块一，并将其 latent diffusion 训练与重构限制到一个 batch，保证该模块的实际兼容性也被检查。
4. 三个模型在冒烟模式下会强制保存 checkpoint 并打印保存标识；总控除了检查子进程返回码，还会检查评估指标标识以及 checkpoint 文件是否真实存在。任一检查失败即记录失败模型、日志与原因，并阻止正式实验开始。
5. 新增单独命令 `python noise_benchmark.py compatibility --gpu 0` 供服务器环境预检；通过结果按 Python 路径、GPU、种子和 Youshu 0 噪声输入哈希缓存。正式 `run` 会复用缓存，环境或代码变化后可用 `--rerun-compatibility-check` 强制重测。

### 已完成验证

- 三个训练入口和总控脚本已通过 Python 编译/语法检查；
- 已通过 `--dry-run` 验证正式总控在预演模式下明确不启动兼容性或训练子进程；
- 使用故意不存在的 Python 可执行文件验证兼容性失败链路：错误被写入 `compatibility_smoke/compatibility_manifest.json`，并以“正式实验未启动”的明确错误结束；未在本地执行任何实际模型训练。

## 13. 兼容性通过缓存的代码/配置变更失效机制（2026-10-14）

兼容性测试缓存已进一步增强：缓存签名除 Python 可执行路径、GPU、训练/噪声种子和 Youshu 0 噪声训练文件哈希外，还会递归计算所选模型项目中 `.py`、`.yaml`、`.yml` 源码与配置文件的 SHA-256 指纹（自动排除数据集、日志、checkpoint、运行产物和 Git 元数据）。因此，只要三个项目的相关代码或配置发生变动，旧的兼容性通过记录就会自动失效，并在下一次正式 `run` 前重新执行测试，而不会误用过期的“通过”状态。已验证指纹可正常生成。

## 14. MultiCBR GPU 评估标签设备一致性修复（2026-10-14）

在实验室服务器的真实 Youshu 兼容性冒烟测试中，CrossCBR 与 ReCoBR 已完成“加载、训练、评估、保存”闭环；MultiCBR 在验证评估阶段报错：预测 Top-K 的索引张量位于 GPU，而 `ground_truth_u_b` 标签矩阵仍位于 CPU，PyTorch 不允许以 GPU 索引访问 CPU 张量。

已在 `MultiCBR/train.py` 的 `test()` 中将传入 `get_metrics()` 的标签改为 `ground_truth_u_b.to(device)`。该改动与 CrossCBR 已有的正确实现一致，仅修复 GPU 评估阶段的设备对齐，不改变训练数据、模型结构、损失函数、指标定义或噪声规则。代码/配置指纹会因此自动使旧的兼容性缓存失效；同步修复后重新执行兼容性测试，将重新检查三个模型，全部通过后才可启动 54 组正式实验。

## 15. MultiCBR GPU NDCG 理想增益缓存设备一致性修复（2026-10-14）

第 14 项修复使标签矩阵与预测张量同在 GPU 后，服务器第二次真实冒烟测试进一步定位到 MultiCBR 的 NDCG 计算：`IDCG()` 创建的理想命中向量，以及 `IDCGs` 缓存张量默认位于 CPU，却在 GPU 上的折损增益计算中参与运算，导致 CPU/GPU 张量混用错误。

已为这两个张量显式指定 `device=device`，实现与 CrossCBR 的已验证 GPU 版本一致。修复仅影响指标计算中张量所在设备，不改变 Recall/NDCG 的数学公式、训练流程或实验数据。再次同步后，兼容性缓存会因源码指纹变化自动失效并完整重测三个模型。
